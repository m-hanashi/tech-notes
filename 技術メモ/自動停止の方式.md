# 自動停止の方式

> 2026-11-13 時点の解説です。その後の変更は反映していないことがあります。

検証環境を、起動から一定時間（例：3時間）で自動的に削除する方式を検討したときに整理した内容です（2026-10-29）。

## 1. 前提知識

### 「停止」と「削除」の違い

| リソース | 止めておけるか | 料金を止めるには |
|---|---|---|
| ECS（API） | タスク数を0にすれば止まる | 止めれば料金はかからない |
| ALB・NAT Gateway | 「停止」という機能がない | 削除するしかない |
| Aurora Serverless v2 | 使われなくなると、自分で休止する | 何もしなくてよい |

料金を確実に止めるには、ALB と NAT Gateway を含む「起動層」を丸ごと削除する必要がある。

### Terraform の state

- Terraform は、「自分が作ったものの一覧」（state）を記録している
- Terraform を使わずに直接削除すると、state には「まだある」と残ったままになり、次に Terraform を実行したときに、エラーや予期しない動きの原因になる
- そのため、消すときも Terraform で行うのが原則

### GitHub Actions のきっかけ

| きっかけ | 意味 | 今回の用途 |
|---|---|---|
| `workflow_dispatch` | 画面のボタンを押したときに実行する | 手動での起動・停止 |
| `schedule` | 決まった時刻に自動で実行する（cron 形式） | 自動停止の見回り |

GitHub Actions から AWS を操作するときは、OIDC を使う。アクセスキーを保存せずに、一時的な許可だけを受け取る方法。

## 2. 方式 A：GitHub Actions の定期実行

```
13:00  「起動」ボタン → Terraform で起動層を作成し、起動時刻を記録する
13:30  見回り → 経過30分 → 何もしない
  …
16:00  見回り → 経過3時間 → Terraform で起動層を削除する
```

- 途中で手動停止した場合：その時点で削除される。以降の見回りは何もしない
- 見回りが遅れたり、飛ばされたりした場合：次の回で削除される
- 注意点：GitHub の定期実行は、混み合うと数分〜数十分遅れることがある。公開リポジトリでは、60日間動きがないと定期実行が自動で無効になる

## 3. 方式 B：起動した処理が待ってから削除

```
13:00  「起動」ボタン → 作成 → そのまま3時間待機
16:00  待機が終わる → 削除
```

- 待っている間も GitHub Actions の利用時間を消費する（非公開リポジトリの無料枠は月2,000分）
- 待機中に処理が中断されると、削除が実行されない

## 4. 方式 C：AWS 側のタイマー

```
13:00  「起動」ボタン → 作成し、AWS に「16:00 に1回だけ実行する」予約を作る（EventBridge Scheduler）
16:00  予約どおりに CodeBuild が起動し、Terraform で削除する
```

- 時刻が正確で、GitHub の遅延や障害の影響を受けない
- Terraform を実行する環境が2か所（GitHub Actions と CodeBuild）になり、権限・設定・バージョンを両方で管理する必要がある

## 5. 比較

| 判断軸 | A | B | C |
|---|---|---|---|
| 確実に消えるか | ○（遅れることはあるが、いずれ消える） | △（中断すると消えない） | ◎ |
| 時刻の正確さ | △（最大30分＋α 遅れる） | ○ | ◎ |
| 部品の少なさ・理解しやすさ | ◎ | ◎ | △ |
| 追加の料金 | なし | 利用時間を消費する | ほぼなし |

自動停止で最も重要なのは「時刻の正確さ」ではなく「いずれ必ず消えること」。
