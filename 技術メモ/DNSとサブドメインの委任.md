# DNS とサブドメインの委任

> 2026-11-13 時点の解説です。その後の変更は反映していないことがあります。

サブドメイン名を決めるために必要な知識を、やさしくまとめます。

---

## 1. ドメイン名は「住所」と同じ階層になっている

ドメイン名は、**右に行くほど大きな区分**です。住所の「都道府県 → 市 → 町 → 番地」を、右から左に読むイメージです。

```
api . tech-notes . m-hanashi . com
番地    町            市          国
```

| 部分 | たとえ | 誰が決めるか |
|---|---|---|
| com | 国 | 世界で決まっている |
| m-hanashi.com | 市（自分が買った土地） | 自分（Cloudflare で取得済み） |
| tech-notes.m-hanashi.com | 町 | 自分で自由に作れる |
| api.tech-notes.m-hanashi.com | 番地 | 自分で自由に作れる |

`m-hanashi.com` を持っていれば、その左側（サブドメイン）は、追加料金なしでいくつでも作れます。

---

## 2. DNS は「名前から行き先を調べる電話帳」

ブラウザや curl は、`api.tech-notes.m-hanashi.com` という名前のままではサーバーにつながれません。DNS という電話帳で、行き先（IP アドレス）を調べてからつなぎます。

電話帳は1冊ではなく、**区分ごとに分かれて**います。この1冊1冊を**ゾーン**と呼びます。

| ゾーン（電話帳） | 持っている人 |
|---|---|
| com の電話帳 | 世界の管理団体 |
| m-hanashi.com の電話帳 | 今は Cloudflare |

電話帳の1行1行を**レコード**と呼びます。例：「api は ○○ に行ってください」。

---

## 3. 委任とは「この先は別の電話帳を見て」と書くこと

Cloudflare の電話帳に、次の1行を書き足します。

> 「tech-notes 以下の名前は、Route 53 の電話帳を見てください」

この1行が **NS レコード**で、この仕組みを**委任**と呼びます。

```
問い合わせ：api.tech-notes.m-hanashi.com はどこ？

  com の電話帳        「m-hanashi.com は Cloudflare に聞いて」
      ↓
  Cloudflare        「tech-notes 以下は Route 53 に聞いて」 ← NS レコード（委任）
      ↓
  Route 53          「api は ALB のこの場所です」           ← ここを Terraform で管理
      ↓
  ALB につながる
```

委任したあとは、`tech-notes` から左の名前は、すべて Route 53 の中で作れます。Cloudflare 側は、最初に1行書くだけです。

10/31 のテストで作った `route53-test.m-hanashi.com` は、Route 53 に電話帳だけを作り、Cloudflare に委任の1行を書かなかった状態です。だから、外からは使われませんでした。

---

## 4. なぜ Route 53 に任せると便利なのか

### API の行き先が、起動のたびに変わる

ALB は起動層にあるので、使うたびに作り直します。作り直すと、ALB の場所も変わります。

Route 53 に電話帳があれば、Terraform が ALB を作るときに「api は新しい ALB の場所です」と**自動で書き換え**られます。Cloudflare の電話帳だと、Cloudflare 用の設定と認証情報が別に必要になります。

### HTTPS の証明書の発行が自動でできる

HTTPS の証明書は、「この名前の持ち主は本物です」という証明書です。ACM が証明書を発行するときは、**その名前の電話帳に、確認用の行を書けるか**を確かめます（DNS 検証）。

電話帳が Route 53 にあれば、Terraform が確認用の行を書けるので、発行まで自動で終わります。

---

## 5. 決めることは2つ：「電話帳をどこから分けるか」と「API の番地」

| 決めること | 例 | あとから変えるときの手間 |
|---|---|---|
| ① 委任する範囲（ホストゾーンの名前） | tech-notes.m-hanashi.com | **大きい**。Cloudflare の NS レコードを書き直し、Route 53 のゾーンも作り直す。証明書も発行し直す |
| ② API のアドレス（ゾーンの中のレコード） | api.tech-notes.m-hanashi.com | **小さい**。Terraform でレコードを1行変え、証明書を発行し直すだけ（自動） |

つまり、**慎重に決めるべきなのは ① の委任する範囲**です。② の API のアドレスは、あとからでも比較的簡単に変えられます。

### 選択肢の違い

```
A：tech-notes を委任、API は api.
   m-hanashi.com（Cloudflare）
   └─ tech-notes.m-hanashi.com（Route 53 に委任）
       ├─ api.tech-notes.m-hanashi.com   ← API
       └─ （発展で画面を作るなら app.tech-notes… などを追加）

B：tech-notes を委任、API もそのまま
   m-hanashi.com（Cloudflare）
   └─ tech-notes.m-hanashi.com（Route 53 に委任）← この名前自体が API

C：aws を委任して、ほかの検証と共用
   m-hanashi.com（Cloudflare）
   └─ aws.m-hanashi.com（Route 53 に委任）
       ├─ tech-notes.aws.m-hanashi.com   ← API
       └─ （将来の別の検証）
```

| 観点 | A | B | C |
|---|---|---|---|
| 名前の短さ | やや長い | 短い | やや長い |
| 発展で画面などを足すとき | ゾーンの中に名前を足すだけ | API の名前を変えるか、別の決め方が必要 | ゾーンの中に名前を足すだけ |
| ゾーンの持ち主 | このプロジェクト | このプロジェクト | 複数のプロジェクトで共用（どの Terraform で管理するかが曖昧） |
| 料金 | ゾーン1つ（月 $0.50） | 同じ | 同じ（共用すれば将来の分は増えない） |

---

## 6. 用語のまとめ

| 用語 | 意味 |
|---|---|
| ドメイン | インターネット上の住所の名前（例：m-hanashi.com） |
| サブドメイン | ドメインの左側に足した名前（例：tech-notes.m-hanashi.com） |
| DNS | 名前から行き先（IP アドレス）を調べる仕組み。電話帳 |
| ゾーン（ホストゾーン） | DNS の電話帳の1冊。Route 53 では「ホストゾーン」と呼ぶ |
| レコード | 電話帳の1行（例：api は ALB の場所） |
| NS レコード | 「この先は別の電話帳を見て」と書く行。委任に使う |
| 委任 | 名前の一部の管理を、別の電話帳に任せること |
| エイリアスレコード | Route 53 独自の、AWS の部品（ALB など）を直接指す行。ALB の場所が変わっても追従する |
| DNS 検証 | 証明書を発行するとき、電話帳に確認用の行を書けるかで、名前の持ち主かを確かめる方法 |
