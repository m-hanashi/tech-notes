# 0002. マイグレーションのツールに goose を使う

2026-11-18 に決定（#25、#31）

## 比較した選択肢

| 選択肢 | 途中で失敗したとき | 特徴 |
|---|---|---|
| A. goose | 1つのファイルを1つのトランザクションで実行するので、DB は実行する前の状態に戻る。記録も進まない | SQL のファイルを書くだけ。Go のプログラムに組み込める |
| B. golang-migrate | トランザクションで包まない。途中までの変更が残り、記録に dirty の印が付いて止まる。人が DB を見て手で直す | 広く使われている。進む用と戻す用の2つのファイルを書く |
| C. Atlas | 設定による | あるべき形を書くと、差分を自動で計算する。高機能だが、覚えることが多い。一部の機能は有料 |

## 決定

A. goose を使う。

## 理由

- 仕様書 7.4 の「マイグレーションが途中で失敗した場合も、DB は変更前の状態に戻る」が、そのまま成り立つ
- 段階5で、マイグレーションを ECS の単発タスクとして自動で実行する。失敗しても人の手で直す必要がないので、自動の流れと相性がよい
- SQL を書くだけなので、覚えることが少ない
- Go のプログラムに組み込めるので、マイグレーションのコマンド（`cmd/migrate`）を API と同じイメージに入れられる（仕様書 7.4）

## 引き受ける課題

- トランザクションに入れられない操作（`CREATE INDEX CONCURRENTLY` など）は、goose でも元に戻らない。こうした操作は、`-- +goose NO TRANSACTION` の印を付けた別のファイルにし、1つのファイルに1つの操作だけを書く
- goose は戻す用（Down）の SQL も書ける。ただし、マイグレーションは追加だけにする決まり（CLAUDE.md）なので、本番で Down を使う場面は想定しない

## 発展

- DB を使う自動テスト（#35）で、マイグレーションを毎回適用してからテストする
