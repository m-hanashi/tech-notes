# HTTP API の基礎

> 2026-11-15 時点の解説です。その後の変更は反映していないことがあります。

段階1で Go の API を作る前に、インフラの経験をもとに、アプリケーションの側から HTTP を見直した内容です。

---

## 1. アプリの仕事は「リクエストを受け取り、応答を1つ返す」

ALB の後ろで、ターゲットのポート（例：8080）で待っているのがアプリです。リクエストも応答も、3つの部分でできた文字の並びです。

| | リクエスト | 応答 |
|---|---|---|
| ① | メソッドとパス（何を、どうしたいか） | 状態コード（結果はどうだったか） |
| ② | ヘッダー（認証のキーなど） | ヘッダー（本文の種類など） |
| ③ | 本文（登録したいメモなど） | 本文（返すメモや、エラーの理由など） |

インフラの側では、主に①を見ていました。アプリの側では、②と③も含めて、どの入力にどの応答を返すかをすべて決めます。

## 2. 状態コード

| 最初の数字 | 意味 |
|---|---|
| 2xx | 成功 |
| 4xx | 呼んだ側の誤り。呼び方を直せば成功する |
| 5xx | アプリの側の誤り。呼んだ側には直せない |

| コード | このプロジェクトで返す場面 |
|---|---|
| 200 | 取得・一覧・要約・ヘルスチェックの成功 |
| 201 | メモの登録に成功した |
| 400 | 入力の誤り |
| 401 | API キーがない、または間違っている（名前は Unauthorized だが、意味は「認証されていない」） |
| 404 | 指定したメモがない。存在しないパスを呼んだ |
| 405 | パスはあるが、メソッドが違う |
| 502・503・504 | AI の誤り・呼び出し回数の制限・時間切れ。ALB も同じコードを返すことがあるので、アプリが返すときは本文に理由を書いて見分ける |

## 3. ヘッダーと本文

- 本文は JSON で書く。`{ }` はひとまとまりのもの、`[ ]` は並び
- `Content-Type: application/json` で、本文が JSON であることを伝える
- エラーのときも、本文の JSON で理由を返す

## 4. API の形

パスは「何を」（リソース）、メソッドは「どうする」を表す。

| メソッド | データを変えるか | 同じものを2回呼ぶと |
|---|---|---|
| `GET` | 変えない | 同じ結果が返るだけ |
| `POST` | 変える | 2回作られる |

要約（`POST /notes/{id}/summary`）は、読むだけに見えるが、呼ぶたびに AI が文章を作り、料金がかかるので `POST` にしている。`GET` にすると、道具が自動で何度も呼び、そのたびに料金がかかるおそれがある。

## 5. アプリの中の部品

| 部品 | レストランにたとえると | 仕事 |
|---|---|---|
| ルーター | 受付 | メソッドとパスを見て、どのハンドラーに渡すかを決める。登録していないパスには 404、メソッドが違えば 405 を自動で返す |
| ハンドラー | 料理人 | リクエストを受けて、応答を作る |
| ミドルウェア | 入店のときに会員証を確かめる係 | どのリクエストにも共通の処理（認証、ログ）をする |

## 6. テストケースの考え方

テストケースは「この入力なら、これが返るべき」という約束。次の4つの見方で挙げる。

| 見方 | 問い |
|---|---|
| 正しい使い方 | ふつうに呼んだら、何が返る？ |
| 間違った使い方 | 呼び方を間違えたら？ |
| 境目の値 | 上限ちょうど、上限を1つ超えたら？ |
| ほかのものの不調 | API が使っているもの（DB、AI）が止まっていたら？ |
