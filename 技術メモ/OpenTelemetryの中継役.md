# OpenTelemetry の中継役（Collector）

> 2026-11-13 時点の解説です。その後の変更は反映していないことがあります。

監視データが、アプリからどのように CloudWatch・X-Ray まで届くのか。その途中にある「中継役（Collector）」が何をしていて、どこに置けるのかをまとめます。用語は `可観測性の用語.md` も参照。

---

## 1. 監視データは3種類

| 種類 | たとえ | 例 |
|---|---|---|
| メトリクス | 体温計や血圧の数字 | 1分間のリクエスト数、エラー率、レイテンシ |
| トレース | 荷物の追跡番号の記録 | 1つのリクエストが、API → DB → Bedrock をどの順に、それぞれ何秒で通ったか |
| ログ | 日記 | 「メモ id=… の取得で、DB の接続に失敗した」 |

---

## 2. アプリの中で起きていること

Go のアプリには、OpenTelemetry の部品（SDK）を組み込みます。SDK は次のことをします。

1. リクエストが来るたびに、「どこを何秒で通ったか」を記録する（トレース）
2. 回数や時間を数える（メトリクス）
3. ためたデータを、決まった形式（**OTLP**。OpenTelemetry の共通の形式）で、どこかへ送る

ポイントは 3 の「どこかへ」です。ここをどこにするかが、今回の論点です。

---

## 3. 中継役（Collector）の仕事

Collector は、**郵便の集配所**のようなものです。

```
アプリ ──OTLP──▶ Collector ──▶ X-Ray（トレース）
                     │
                     └──────▶ CloudWatch（メトリクス）
```

| 仕事 | 内容 |
|---|---|
| 受け取る | アプリから OTLP でデータを受け取る |
| まとめる | 少しずつ届くデータを、ある程度ためてからまとめて送る（通信の回数を減らす） |
| 加工する | 「どの環境のデータか」などのラベルを足す。不要なデータを捨てる |
| 宛先の形式に合わせて送る | X-Ray 用、CloudWatch 用など、宛先ごとの形式と認証で送る |

アプリは「集配所に渡す」ことだけを知っていればよく、**宛先のことを知らなくて済みます**。宛先を Grafana Cloud に変えたくなったら、集配所の設定（住所録）を書き換えるだけです。アプリのコードは変えません。

AWS は、Collector に AWS 向けの部品を加えた版を **ADOT**（AWS Distro for OpenTelemetry）として配布しています。

---

## 4. 置き場所の3つの案

### A. 同じタスクに同居（サイドカー）

```
┌─────── ECS のタスク ───────┐
│  API のコンテナ              │
│     │ localhost              │
│     ▼                        │
│  Collector のコンテナ        │──▶ X-Ray・CloudWatch
└──────────────────────────────┘
```

- 1つのタスクの中に、API と Collector の2つのコンテナを入れます。
- 同じタスクのコンテナは同じネットワークを共有するので、API は `localhost` に送るだけです。
- タスクが増えると、Collector も一緒に増えます。起動も停止も一緒です。
- タスクの CPU とメモリを、Collector の分だけ少し多めに割り当てます。

### B. 置かない（アプリから直接送る）

```
API のコンテナ ──────────────▶ AWS の受け口（X-Ray など）
```

- AWS には OTLP を直接受け取れる受け口もあります。ただし、AWS の認証（リクエストへの署名）が必要で、その処理がアプリ側に入ります。
- データの種類によって、受け口の対応状況が違います。
- 宛先を変えるときは、アプリの設定を変えることになります。

### C. 専用のサービスとして1か所に置く

```
API のタスク ─┐
API のタスク ─┼──▶ Collector だけのサービス ──▶ X-Ray・CloudWatch
API のタスク ─┘
```

- 何十ものタスクがある大きな環境で、Collector の数を抑えたいときに使います。
- 今回は API のタスクが1〜2個なので、部品が増えるだけで利点がありません。

---

## 5. 比べると

| 観点 | A. サイドカー | B. 直接送る | C. 専用サービス |
|---|---|---|---|
| アプリが宛先を知る必要 | ない | ある | ない |
| 宛先の切り替え（第2章の発展） | Collector の設定だけ | アプリの設定を変える | Collector の設定だけ |
| 部品の数 | タスクにコンテナが1つ増える | 増えない | サービスが1つ増える |
| 料金 | タスクの CPU・メモリが少し増える | 増えない | 常に動くタスクが1つ増える |
| 向いている規模 | 小〜中 | とても小さい・試作 | 大 |

---

## 6. A を選んだ場合に、実装で決めること

| 項目 | 内容 |
|---|---|
| 起動の順番 | Collector が起動してから API を起動する（ECS のコンテナの依存関係で指定する）。先に API が動くと、最初のデータが送れない |
| Collector が止まったとき | Collector が落ちても API は動き続けるようにするか、タスクごと入れ替えるか。前者は監視データが一時的に欠けるが、利用者への影響はない |
| ログの経路 | ログは Collector を通さず、ECS の標準の仕組み（標準出力 → CloudWatch Logs）で送る。ログの中にトレースの ID を書き、ログとトレースを行き来できるようにする |
| 通信の経路 | Collector から AWS への通信は、NAT Gateway を通る（第4章の構成のまま） |
