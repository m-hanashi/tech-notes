# 可観測性の用語

> 2026-11-13 時点の解説です。その後の変更は反映していないことがあります。

目的3「可観測性」の完成条件を検討したときに整理した内容です（2026-10-29）。

## 1. 例：「メモを AI で要約する」リクエストが遅かった場合

```
利用者 ──▶ ALB ──▶ API（Go）──▶ Aurora（メモの本文を読む）
                      │
                      └──▶ Bedrock（要約を作る）
```

利用者からは「3秒かかった」としか分からない。可観測性は、この3秒の内訳と理由を、外から分かるようにするための仕組み。

可観測性は、次の3種類のデータで実現する。

| データ | わかりやすく言うと | 答えられる問い |
|---|---|---|
| メトリクス | 数値の推移（グラフ） | 「今、何かおかしいか？」 |
| トレース | 1つのリクエストが、どこをどう通ったかの記録 | 「どこで時間がかかっているか、どこで失敗したか？」 |
| ログ | 処理ごとの詳しい記録 | 「なぜ失敗したのか？」 |

メトリクスで異常に気づく → トレースで場所を絞る → ログで原因を知る、という順にたどる。

## 2. メトリクス

- 一定の間隔で集計した数値。グラフにして推移を見る
- 例：1分あたりのリクエスト数、エラーの割合、応答時間
- レイテンシ（応答にかかった時間）は、平均ではなく p95（遅いほうから5%の位置の値）などで見るのが一般的。平均では、一部の利用者だけが極端に遅い状況を見逃すため

## 3. トレースとスパン

- トレース：1つのリクエストが通った道筋の、全体の記録
- スパン：その中の一つひとつの区間の記録

```
トレース ID: abc123
├─ API 全体            ████████████████████████████ 3.0秒
│  ├─ DB 読み込み      ██ 0.1秒
│  └─ Bedrock 呼び出し    ████████████████████████ 2.8秒  ← 原因はここ
```

## 4. ログと構造化ログ

- ログ：処理ごとに出力する、詳しい記録
- 構造化ログ：項目名つきの決まった形式（JSON）で出力するログ

```json
{"time":"13:05:02","level":"error","trace_id":"abc123","message":"Bedrock timeout","duration_ms":2800}
```

- 項目ごとに検索・集計できる
- ログに trace_id を入れておくと、トレースからログへ、ログからトレースへ、相互にたどれる

## 5. 計装（instrumentation）

- アプリが、メトリクス・トレース・ログを出力するための仕組みを組み込むこと
- 自動計装：ライブラリを入れるだけで、HTTP の受付や DB の呼び出しなどを自動で記録する
- 手動計装：「ここからここまでを1つの区間として記録する」と、コードに自分で書く
- Go は、Python に比べて手動で書く部分が多め

## 6. OpenTelemetry

- 計装のための業界標準の仕組み
- これがない場合：監視ツールごとに専用の書き方で計装する必要があり、ツールを変えるとアプリのコードも書き直しになる
- これを使う場合：アプリは標準の方式でデータを出し、どのツールに送るかは設定で切り替えられる

```
アプリ（OpenTelemetry で計装）──▶ 送り先を設定で選ぶ ──▶ X-Ray / CloudWatch / Datadog / Grafana など
```

## 7. そのほかの用語

| 用語 | 意味 |
|---|---|
| ダッシュボード | 複数のグラフを1画面にまとめたもの。今回は Terraform で作り、環境を作り直しても再現されるようにする |
| 外形監視 | システムの外から定期的に API を呼び、利用者から見て正常かを確かめる監視。内部の指標が正常でも、外からつながらない状態を見つけられる |
| ランブック | 「この警告が出たら、まずここを見て、次にこれを確認する」という、障害対応の手順書 |
