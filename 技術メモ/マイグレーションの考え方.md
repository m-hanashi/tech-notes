# マイグレーションの考え方

> 2026-11-13 時点の解説です。その後の変更は反映していないことがあります。

DB のマイグレーションが、なぜ今のようなやり方になったのか。その経緯と、技術的な考え方をまとめます。

---

## 1. そもそも何が難しいのか

アプリのコードと、DB の形（テーブルや列。**スキーマ**と呼ぶ）は、**いつも組み合わせで正しく動く必要があります**。

| | アプリのコード | DB |
|---|---|---|
| 入れ替え | 新しいものに丸ごと取り替えられる。古いものに戻すのも簡単 | **中にデータが入っている**。丸ごと取り替えられない。消したデータは戻らない |
| 置き場所 | 何台にでも同時に置ける | 1つだけ（みんなで共有している） |

つまり、**アプリは「取り替える」もの、DB は「育てる」もの**です。この性質の違いが、マイグレーションの難しさの根っこです。

---

## 2. 経緯：どう変わってきたか

### 段階1：手作業の時代

- DB の担当者（DBA）が、リリースの日に SQL を手で実行していました。
- 問題：
  - 「本番の DB に、どの変更まで入っているか」が、人の記憶や手順書に頼っていた
  - 開発環境・検証環境・本番環境で、DB の形が少しずつずれていく
  - 手順を間違えると、データが壊れる

### 段階2：マイグレーションのツールの登場

2000年代の半ばごろから、Ruby on Rails のマイグレーション機能や、Java の Flyway・Liquibase などのツールが広まりました。考え方の中心は、次の3つです。

| 考え方 | 内容 |
|---|---|
| 変更をファイルにする | 「列を足す」などの変更を、番号付きのファイル（例：`0001_create_notes.sql`、`0002_add_tag.sql`）にして、コードと一緒に Git で管理する |
| 順番に適用する | ツールが、番号の順に適用する |
| 適用済みを DB に記録する | DB の中に「どの番号まで適用したか」を記録する表を作る。ツールは、まだ適用していない番号だけを実行する |

これで、**「DB の形の変更」もコードと同じように、レビュー・再現・自動化ができる**ようになりました。どの環境でも、同じファイルを順に適用すれば、同じ形になります。

### 段階3：自動デプロイの時代（いつ実行するか問題）

CI/CD で自動デプロイするようになると、**「マイグレーションを、デプロイの流れのどこで実行するか」**が問題になりました。

| やり方 | 広まった背景 | 弱点 |
|---|---|---|
| アプリの起動時に実行する | 一番手軽。サーバーが1台なら問題が少ない | サーバーが複数台だと、同時に実行しようとして競合する。失敗するとアプリも起動しない |
| デプロイの前に、別の処理として1回だけ実行する | サーバーが複数台になり、起動時の実行では困るようになった | 仕組みが1つ増える |

今は、**「アプリとは別に、デプロイの前に1回だけ実行する」**が主流です。
- Heroku の「release phase」、Kubernetes の「Job」、ECS の「単発タスク（run-task）」など、多くの基盤がこのための仕組みを用意しています。
- このプロジェクトで選んだ A（ECS の単発タスク）も、この流れに沿ったものです。

### 段階4：止めずに変える時代（互換性の問題）

サービスを止めずにデプロイする（ローリングアップデート、ブルーグリーンなど）のが当たり前になると、もう1つの問題が見えてきました。

**切り替えの途中は、古いアプリと新しいアプリが、同じ DB を同時に使う**、という問題です。

```
時間 →
古いアプリ  ■■■■■■■■■■□□□□□   （少しずつ止まる）
新しいアプリ □□□□□■■■■■■■■■■   （少しずつ増える）
DB の形    ──旧──│──────新──────
                 ↑ マイグレーション
          この区間は、古いアプリも「新しい形の DB」を使う
```

さらに、新しいアプリが壊れていて**自動で切り戻した**場合は、古いアプリが「新しい形の DB」で動き続けます。

そこで生まれたのが、**「拡張と縮小」（Expand / Contract）**という考え方です。

| 段階 | やること | 例：列の名前を title から subject に変える |
|---|---|---|
| 拡張（Expand） | 古いアプリが困らない形で、新しいものを**足す** | subject 列を足す。アプリは両方に書き込む |
| 移行 | データを移し、アプリを新しいものに切り替える | 既存のデータを subject に写す。アプリは subject だけを読む |
| 縮小（Contract） | 誰も使わなくなった古いものを**消す** | 次以降のデプロイで、title 列を消す |

**一度に「消す」「名前を変える」をしない**ことで、どの瞬間にも、古いアプリと新しいアプリの両方が動けるようにします。

## 3. このプロジェクトでの形

```
main にマージ
  ↓
イメージを作る（アプリとマイグレーションのコマンドが入っている）
  ↓
新しいタスク定義を登録する
  ↓
ECS の単発タスクで、マイグレーションを実行する ──失敗──▶ デプロイを中止（古いバージョンが動き続ける）
  ↓ 成功
サービスを新しいタスク定義に切り替える ──起動失敗──▶ 自動で切り戻し（古いバージョン＋新しい形の DB）
  ↓ 正常
「最後に正常に動いたバージョン」を記録する
```

自動で切り戻したときは、「古いバージョン＋新しい形の DB」の組み合わせになります。だから、**マイグレーションは拡張だけにして、古いバージョンでも動く形にする**というルールが必要です。

## 4. PostgreSQL の利点と、その限界

### 利点：形の変更もトランザクションでできる

PostgreSQL では、テーブルの形を変える操作（`CREATE TABLE`、`ALTER TABLE` など）も、トランザクションの中で実行できます。

- マイグレーションの途中で失敗しても、**全部なかったことになり、DB は変更前の状態に戻ります**。
- MySQL では、形を変える操作をすると、その時点で自動で確定してしまいます。途中で失敗すると、中途半端な状態が残ることがあります（詳しくは `PostgreSQLとMySQLの違い.md`）。

### 限界

| 注意点 | 内容 | このプロジェクトでは |
|---|---|---|
| トランザクションに入れられない操作がある | 例：使用中のテーブルを止めずに索引を作る `CREATE INDEX CONCURRENTLY` | 使うときは、その操作だけ別のマイグレーションにする |
| 形の変更中は、テーブルが一時的に使えなくなることがある | `ALTER TABLE` は、テーブルに強い鍵（ロック）をかける。データが多いと、その間アプリが待たされる | データが少ないので、ほぼ影響しない。データが増えた場合の注意として覚えておく |
| 戻すのは「失敗したとき」だけ | 成功したマイグレーションは確定する。あとから戻すには、戻すためのマイグレーションを別に書く | 拡張だけにするルールで、戻す必要自体を減らす |

## 5. 用語のまとめ

| 用語 | 意味 |
|---|---|
| スキーマ | DB の形（テーブル、列、索引など） |
| マイグレーション | スキーマを変える作業。また、その変更を書いたファイル |
| 単発タスク（run-task） | ECS で、1回だけ動いて終わるタスク。マイグレーションなどに使う |
| トランザクション | 複数の操作を「全部成功するか、全部なかったことにするか」の1つのまとまりとして扱う仕組み |
| ロック | ほかの処理が同時にデータを変えないように、一時的にかける鍵 |
| 拡張と縮小（Expand / Contract） | スキーマの変更を「足す → 移す → 消す」に分け、古いアプリと新しいアプリの両方が動けるようにする考え方 |
