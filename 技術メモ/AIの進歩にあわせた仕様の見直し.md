# AI の進歩にあわせた仕様の見直し

> 2026-11-24 時点の解説です。その後の変更は反映していないことがあります。

段階1の #29（Bedrock で要約する）のモデル選びの途中で、仕様書を書いた時期（2026年10月）からの AI の変化を、仕様書に反映するかを見直すことにしました。この文書は、何を、なぜ見直すのかをまとめたものです。

## 1. そもそも何を見直すのか

仕様書は、「どの AI を使っても成り立つ書き方」を目指して書きました。ところが、この1〜2年で AI のモデルの使い方そのものが変わり、仕様書の前提のいくつかが、新しいモデルでは成り立たなくなっています。

見直しの対象は、AI の進歩の影響が大きい次の2つです（基盤・CI/CD・SRE の章は、影響が小さいので対象にしません）。

| 区分 | 何についての決まりか | 見直すこと |
|---|---|---|
| A. AI 機能 | API が Bedrock を呼んで要約を返す部分（仕様書 2.6・4.2・5.2） | A1：ばらつきの抑え方、A2：thinking の扱い |
| B. 開発での AI 活用 | Claude Code で開発する進め方（仕様書 1.4・5.1・9.3） | B2：AI 駆動開発に完成条件を設けるか |

インフラにたとえると、「OS のバージョンが上がって、手順書に書いた設定項目の一部が廃止された」状態です。手順書（仕様書）の目的はそのままで、設定のやり方を新しい版に合わせて書き直します。

## 2. A1：ばらつきの抑え方

### 今の仕様書

仕様書 5.2 は「温度（出力のランダムさ）を低めに設定する」と書いています。温度は、AI が次の言葉を選ぶときに、どれくらい冒険するかを決める数値です。0 に近いほど、毎回同じような答えになります。

### 何が変わったか

Anthropic の新しいモデル（Claude 4.7 以降。候補の Haiku 5.5 も含む）は、**温度を既定値以外にするとエラー（400）を返します**。さらに、2026-10-21 版の Claude API では、温度の指定そのものを受け付けません。

理由は、新しいモデルが内部で「考えてから答える」（A2）ようになり、温度をいじると考える処理の質が落ちるためです。つまり、仕様書のとおりに温度を下げると、本命のモデルが動きません。

### 代わりの方法

ばらつきを抑えたい理由は、「3行以内の箇条書き」という形を守らせたいからでした。今はこれを、温度ではなく次の方法で守るのが定番です。

| 方法 | 内容 | 仕組みのたとえ |
|---|---|---|
| 構造化出力（Structured Outputs） | 返す形を JSON スキーマで指定する。モデルはその形でしか返せない | 入力欄が決まった申請フォーム。自由記述させない |
| 形のチェック | 返ってきたものが3行以内か、プログラムで確かめる（仕様書 5.2 にすでにある） | 受け取った設定ファイルの構文チェック |

構造化出力は、Bedrock の Claude でも使えます（Converse API での渡し方は、実装のときに確かめます）。たとえば「`lines` という配列で、要素は1〜3個の文字列」と指定すれば、4行以上は返ってきません。#34（3行を超えたときの扱い）も、これでほぼ解決します。

ただし、構造化出力に対応していないモデルもあるため、モデル選びの基準に加える必要があります。

## 3. A2：thinking の扱い

### thinking とは

新しいモデルは、答える前に内部で「考える」処理をします（thinking）。難しい問題では質が上がりますが、そのぶん次の影響があります。

- **遅くなる**：考える分だけ、答えが返るまでの時間が延びる
- **料金が増える**：考えた分も出力のトークンとして課金される

Haiku 5.5 は、何も指定しないと thinking が有効で、考える量（effort）は「中くらい」（`medium`）です。

### なぜ仕様書に入れる必要があるか

| 仕様書の決まり | thinking との関係 |
|---|---|
| 8.3：要約の 95% が10秒以内 | 考える量が多いと、10秒を超えやすい |
| 5.2：出力のトークン数に上限を設ける | 考えた分も上限に含まれる。上限が小さいと、考えている途中で打ち切られ、要約が空になる |
| 5.2：トークン数を記録して料金を出す | 考えた分を分けて見ないと、なぜ料金が増えたか分からない |

要約は難しい推論が要らない仕事なので、考える量は「少なめ」（`low`）にするか、止める（`disabled`）のが合っていると見込んでいます。どちらにするかは、実際に呼んで、速さと質を比べて決めます。

インフラにたとえると、「DB の問い合わせに、既定で詳しい実行計画の分析が付くようになった」状態です。軽い問い合わせには不要なので、明示的に切る設定が要ります。

## 4. B2：AI 駆動開発に完成条件を設けるか

### 今の仕様書

仕様書 5.1 は、Claude Code で開発するときのルール（説明できない変更は入れない、など）を定めていますが、「AI 駆動開発そのものには、完成条件を設けません」と書いています。

### 何が変わったか

仕様書を書いた時点では、AI 駆動開発は「開発の道具」の扱いでした。その後、AI に任せられる範囲が大きく広がり、企業のエンジニアにとって「AI に何を任せ、人が何を判断し、どう品質を保ったか」が、それ自体で関心の高い題材になっています。

このプロジェクトでは、すでに次のことをしています。

- AI がコードを書き、利用者がテストケースを挙げる
- PR の前に `/code-review` でレビューし、指摘を1件ずつ評価する
- PR の説明に「判断したこと」を書く
- 危険な操作を、Claude Code の権限設定で禁止する

これらは今、記録として散らばっています。完成条件にすると、「何を確かめたら達成か」と「どこに証跡があるか」が決まり、ほかの目的（2.2〜2.8）と同じ形で示せます。

### 決定（2026-11-24）

第2章に目的を1つ足し、2.9「AI 駆動開発」とします。MVP の完成条件は、今すでにやっていることだけにします。追加の作業がほとんどなく、すでにある記録に「何の証跡か」という意味を与えるだけで済むためです。CI での AI レビューなど、料金がかかるものは発展に置きます。

| 完成条件 | 検証方法 | 証跡 |
|---|---|---|
| AI が書いた変更は、すべて PR とレビューを通して main に入っている | PR の履歴を確かめる | PR、`/code-review` の指摘を評価した記録 |
| 危険な操作（apply・push・マージなど）を、AI が実行できない | 禁止した操作を AI に実行させ、拒否されることを確かめる | `.claude/settings.json`、拒否された記録 |
| 人が判断したことを、AI の作業と分けて残している | PR の説明を確かめる | PR の「判断したこと」、ADR |

比べた案：第2章には足さず、5.1 に記録の見方だけを足す案と、今のままにする案。どちらも、読み手が何を確かめればよいかが曖昧なまま残るため、選ばなかった。

## 5. 相談の途中で追加した見直し：要約の保存

A1 に入る前に、「要約の 95% が10秒以内は必須か。非同期にして DB に記録してもよいのでは」という論点が出ました。

- 10秒は仕様書 8.3 でも仮の値。非同期にしても時間の目標は残り、「応答まで」が「完了まで」に変わるだけ
- 要約を作る時点を3案で比べた
  - 登録と同時（同期）：登録の SLO（300ミリ秒）と、「AI が壊れても、ほかの機能は動く」（2.6）を守れない
  - 登録のあと（非同期）：キュー・ワーカー・再試行が要り、負荷試験でメモを作るたびに AI が呼ばれる
  - 初めて頼まれたとき：今の作りに保存を足すだけで済む

**決定（2026-11-24）**：同期のまま、初めて要約を頼まれたときに AI を呼んで DB に保存し、2回目以降は保存したものを返す（キャッシュアサイド）。

- 保存するもの（案）：要約の本文、モデル名、入力・出力・thinking のトークン数、かかった時間、作った時刻
- 同じメモへの同時の依頼で2回呼ばれても、DB の一意制約で保存は1件にする
- MVP にはメモの更新がないため、保存した要約が古くなることはない
- 仕様書 5.2 の「要約は DB に保存しない」と、2.6 の発展の「保存して再利用する」を直す
- 非同期は発展のまま。実際に測って時間に収まらなければ、改めて検討する

**決定（2026-11-24）**：要約の SLO は分けて数える。AI を呼んだ回のレイテンシは要約の基準（10秒）、保存したものを返した回は通常の機能の基準（300ミリ秒）で数える。可用性は、どちらも要約として数える。保存したものを返す速い応答が混ざると、AI の遅さが隠れるため。

**決定（2026-11-25）**：仕様書 2.8・4.4・4.5 の「AI の出力を保存や操作に使わない」を、「そのメモの要約としてだけ保存して返し、ほかのデータの変更や処理の判断には使わない」に直す。不適切な要約が残り続けることは引き受ける課題とし、作り直しは発展にする。経緯は `技術メモ/プロンプトインジェクションと出力の保存.md`。

## 6. 見直さなかったもの

| 候補 | 見送った理由 |
|---|---|
| A3：品質評価（AI に採点させる）を MVP に上げる | 段階1が長引く。発展のまま |
| A4：要約以外の AI 機能（エージェント、MCP など） | 題材の見直しに近く、範囲が大きく広がる |
| B1：AI のコードレビューを CI に入れる | API の料金と、秘密情報の設定が要る |
| B3：AI に任せる範囲を広げる | 学習の目的と引き換えになる |
