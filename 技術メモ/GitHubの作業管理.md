# GitHub での作業管理

> 2026-11-15 時点の解説です。その後の変更は反映していないことがあります。

GitHub をはじめて本格的に使う人向けに、Issue・PR・マイルストーンの関係と、このプロジェクトでの使い方の流れをまとめます。

---

## 1. 登場する4つのもの

| もの | たとえ | 中身 |
|---|---|---|
| リポジトリ | プロジェクトの「書類棚」 | コード・仕様書・記録など、すべてのファイルと、その変更の履歴 |
| Issue（イシュー） | 1件ごとの「付箋」 | 「やること」「決めること」「見つけた不具合」を1件ずつ書く。番号（#1、#2…）が自動で付く。コメントで議論でき、終わったら「閉じる」 |
| Pull Request（PR） | 「この変更を棚に入れてよいか」の申請書 | ブランチで行った変更を main に取り込む前に、差分を見せてレビューを受ける。CI はここで動く |
| マイルストーン | 付箋をまとめる「束」 | 複数の Issue を1つの目標にまとめる。「何件中何件が閉じたか」が、進み具合（%）として表示される |

ラベルは、付箋に貼る「色シール」です。例：`未決事項`、`バグ`、`ドキュメント`。絞り込みに使います。

---

## 2. つながり方

```
マイルストーン「段階1：手元で API を作る」   進み具合 3/5（60%）
  ├─ Issue #4  メモの作成 API を作る         ✅ 閉じた ← PR #10 で解決
  ├─ Issue #5  メモの取得 API を作る         ✅ 閉じた ← PR #11 で解決
  ├─ Issue #6  AI のモデルを選ぶ（未決事項）  ✅ 閉じた ← 比較の結果を ADR に記録
  ├─ Issue #7  AI 要約の API を作る          ⬜ 開いている（作業中の PR #13）
  └─ Issue #8  タイムアウトの扱いを作る      ⬜ 開いている
```

- PR の説明に `Closes #7` と書いておくと、その PR を main にマージしたときに、Issue #7 が自動で閉じます。
- Issue の画面には「どの PR で解決したか」が、PR の画面には「どの Issue のための変更か」が、それぞれ表示されます。
- これで「なぜこの変更をしたのか（Issue）」と「何を変えたのか（PR）」が、後から行き来できます。

---

## 3. このプロジェクトでの1日の流れ（例）

1. **始める前**：マイルストーン「段階1」を開き、開いている Issue から1つ選ぶ（例：#7 AI 要約の API）
2. **作業**：ブランチを作り、Claude Code と一緒にコードを書く
3. **PR を出す**：ひな形（`.github/pull_request_template.md`）に沿って、次のことを書く
   - `Closes #7`（マージのあとに apply が要る Terraform の変更は `Refs #7`）
   - 変更の内容と、判断したこと（第5章の決まり）
   - 確認の欄の「変わること」と「なぜ」（第6章の関所）。AI が会話で整理した内容を、理解してから書き写す
4. **CI が動く**：テストや検査が通るのを待つ
5. **自分でマージする**：Issue #7 が自動で閉じ、マイルストーンの進み具合が上がる。`Refs` にした場合は、apply の結果を Issue に書いてから、手で閉じる
6. **途中で決めることが出てきたら**：新しい Issue を作り、`未決事項` のラベルを付ける。決めたら、理由を ADR に書き、その Issue を閉じる

## 4. 今の検討メモとの対応

| 今（検討メモ） | リポジトリを作ったあと |
|---|---|
| 「未決定事項」の表 | `未決事項` ラベルの付いた Issue |
| 段階0〜7の表 | マイルストーン（段階ごとに1つ） |
| 「8. 選定理由の記録」 | docs/adr/ の ADR（1つの判断に1ファイル） |
| 検討メモそのもの | 設計段階の記録として残す（それ以降は更新しない） |

## 5. 案の比較

| 案 | 向いている場面 |
|---|---|
| A. Issue とマイルストーン | 作業と変更（PR）を結びつけて残したいとき。1人でも数人でも使える |
| B. Markdown のまま | 作業が少なく、PR との結びつきが要らないとき |
| C. A に加えて、かんばんのボード（GitHub Projects） | 数人で「誰が何をしているか」を見たいとき。1人では管理が重くなりやすい |

---

## 6. Claude Code との関係

Claude Code は `gh` コマンドで、Issue の一覧を見る、Issue を作る、PR を作る、といった操作ができます。

例：「段階1の開いている Issue を見せて」「この相談で出た未決事項を Issue にして」。

ただし、PR のマージは AI が行わない決まりです（仕様書 6.3）。マージは必ず自分で行います。

---

## 7. 用語

| 用語 | 意味 |
|---|---|
| ブランチ | 本流（main）から分かれた作業用の流れ。main を壊さずに変更を試せる |
| マージ | ブランチの変更を main に取り込むこと |
| `Closes #番号` | PR の説明に書くと、main にマージしたときに、その番号の Issue が自動で閉じる（`Fixes`、`Resolves` も同じ） |
| ラベル | Issue や PR に付ける分類の目印 |
| マイルストーン | Issue をまとめた目標。進み具合が % で表示される |
